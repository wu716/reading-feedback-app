# 项目反馈、每日明细与周期报告

源码版本 **2.0.26**，Android 源码 **versionCode 68**，网页资源标识 **20261023feedback1**。基线 `e9f994f`。本记录描述书然端实现；生产部署和知间真实联调分别验收。

## 使用流程与需求对应

| 需求 | 实现入口与行为 |
| --- | --- |
| 创建项目时填写任务 | 项目 → 新建项目：使用“预期结果”；直接写具体任务、阶段名称和属性，可连续增加。首次命名阶段使用初始阶段；未分阶段的任务也在项目页直接可见。 |
| 计划时新增任务 | 项目 → 计划周期与复盘 → 制定一轮计划：可选已有任务，也可直接写阶段任务。新增任务和计划在同一事务保存，原阶段入口继续共用这些任务。 |
| 整个项目作为工作 | 任务拆分可选。不选任务也能保存计划，范围标为整个项目；预期结果留空时沿用项目预期结果或项目名称。 |
| 自选反馈日期 | 应用内日历连接本轮起止日期；每天、每周指定星期、具体日期，支持跨月以及逐日增补/跳过。保存时生成独立日期节点。 |
| 自定义成果 | 每次交付物和检查依据由用户填写，成果形式可多选或不限。字数是可选标准，不默认出现必须达到的字数。 |
| 多形式提交 | 长期目标 → 每日记录上方“项目推进与成果反馈”：文字、HTTP/HTTPS 链接、图片、文档、音视频、实践说明，可组合提交。单文件 25 MB，每版最多 8 个附件，账号附件总量 500 MB。 |
| 提交与检查分开 | 提交后为“待检查”；用户按实际成果选择通过或待补充，并填写依据。外部链接和附件不能自动计算字数时，明确标为待人工检查。 |
| 迟交、补交、版本 | 每次提交保留版本与实际时间，关联原截止日期。首次提交决定是否迟交，准时提交后的晚间补充不改成首次迟交。跳过需写原因，可恢复，调整保留事件记录。 |
| 每日项目推进 | 引用原工作区间、已完成任务、推进/卡点/下一步和项目状态变更，不把项目区间再次加入长期方向的时间合计。此前待补交节点分页保留，不限最近 30 天。 |
| 长期方向详细填写 | 复用现有活动明细、消费和注意力模型，八方向始终可见，每个方向可记多条内容/时长/感受；写作字数、阅读分类、定投金额等保留。每方向可单独核对“本日没有”，整日核对也保留。 |
| 提醒 | 沿用账号的应用内、系统通知、邮件开关和每日记录提醒偏好。节点提醒可在计划中选择开启；已提交/通过/跳过不继续催交，需补充则可再提醒。邮件失败最多尝试 5 次，按退避时间重试，发送状态可在每日反馈下方查看。 |
| 日周月季年报 | 项目推进、逐书投入、八方向对比、最近六期变化和来源明细。按日期使用节点日历/完整度日历，季度增加阶段里程碑，年度显示成果目录；时间和金额分开。 |
| 缺记与跨期比较 | 同长度的已发生区间比较，不计未来日期；某方向未记录也未核对时，图形留空，不能因其他方向有记录就画成零。图形附核对天数和数据表。 |
| 自动报告及修订 | 保存活动/提交/检查或接收来源修订后刷新相关报告；整日确认生成日报提醒，生产调度器每小时补生成最近已结束的各类周期报告。内容不变不新增版本，补记保留旧版。日报周报基础报告可用，月季年报及深度跨期趋势沿用现有套餐限制。 |
| 知间逐日逐书联动 | 已对齐知间 0.1.16 的双向确认与签名游标协议；用户最终核对两端账号后，书然服务器每 5 分钟自动拉取。提供撤销、完整快照替换、修订去重与只读时间投影；同名书不同来源不合并。手动记录可显式引用同一知间活动去重，说明与核对事件保留。 |

## 数据与兼容

- 在现有 `ensure_schema()` 中注册新增模型，由 `create_all` 增量建表，不删除、搬移或批量改写旧业务表。阶段承诺、30 秒调整、开始条件、实际投入区间和历史反馈继续保留。
- 新增表：`feedback_occurrences`、`feedback_submissions`、`feedback_attachments`、`feedback_reports`、`feedback_deliveries`、`reader_receiver_accounts`、`reader_pairings`、`reader_bindings`、`reader_reading_days`。
- 每方向核对状态扩展在原长期方向 JSON 中。历史整日确认按八方向均已确认读取；旧客户端的保存语义保持兼容。同步来源修订改变记录后，仅将阅读方向改为待核对，递增原账本修订号，旧草稿保存返回冲突。
- 知间来源记录按服务实例、授权账号、日期、稳定书籍 ID 识别。重复或旧快照不叠加；同修订号不同内容返回 409。完整当日快照可以通过明确空数组移除源条目；保留用户补充说明，不再计入已移除来源的时长。
- 手动阅读与同步阅读默认分别记录；用户核对为同一段时建立引用，保留原说明且不重复计时。不能凭书名自动判断同一活动。历史累计值仅保留为基线，不分配给未知日期。
- 附件存储与公开 `/uploads` 分开，下载要求当前账号登录和归属校验，使用附件下载响应。阿里云 Compose 新增持久卷 `feedback_data`，请与数据库、`uploads_data` 一起备份。业务 CSV 备份和个人 JSON 导出包含新业务记录；个人导出排除服务令牌哈希和本机存储键，原附件可在反馈节点下载。
- 系统调度仅在生产环境启动。网页打开时仍可查询到期反馈，邮件队列由服务器调度发送。邮件 465 使用隐式 TLS，587 使用 STARTTLS（依据服务器设置）。
- 没有开启每日记录提醒时，新报告只进入应用内；开启后才沿用系统通知/邮件开关，不因升级自动替用户开启每日催填或报告邮件。

## 用户执行生产更新

旧 Cloud Run 工作流改为仅 `workflow_dispatch` 手动触发，推送 `main` 不自动部署云服务。安卓源码版本变化仍可触发既有构建/发布流水线；其结果与香港生产部署分别验收。

Windows PowerShell：

```powershell
ssh ubuntu@43.161.238.165
```

登录 Ubuntu 后：

```bash
sudo -i
cd /opt/shuran-app && git pull origin main && cd deploy/aliyun && docker compose up -d --build
curl --retry 12 --retry-delay 3 --retry-all-errors --retry-max-time 90 --connect-timeout 5 --max-time 10 -fsS http://127.0.0.1:8000/health
docker compose logs --tail=80 app
# 更新服务器下载入口的 APK，保留旧包并核验摘要、实际清单和下载接口
cd /opt/shuran-app && bash deploy/aliyun/install-apk-2.0.26.sh
```

健康检查应显示 `version` 为 `2.0.26`、`ui_version` 为 `20261023feedback1`。首次建表属于本次应用启动流程。请保留数据库和所有持久卷，不运行 `down -v`。

`.env` 中的 `SMTP_*` 和真实邮箱决定邮件能否实际发送，`PUBLIC_APP_URL` 决定邮件回站地址。知间尚未部署配置和联调时，保持 `READER_API_URL`、`READER_CLIENT_ID`、`READER_CLIENT_SECRET` 为空，界面会显示尚未配置。来源就绪后由两端管理员按协议配置对应机器身份，凭证不提交 Git、不放客户端。生产启用还要求书然已配置安全且稳定的 `SECRET_KEY`。
