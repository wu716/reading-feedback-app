## 已查明的保存链路

- `static/js/projects.js` 的 `detailForm` 提交分支一次提交任务名称、阶段、估时、说明、完成标准、步骤和阻碍等字段。空白文本通过 `value || null` 发送为空值。
- `app/routers/projects.py` 的 `update_task()` 在写入前先比较 `stage_id` 和 `acceptance_criteria`。移出当前阶段、实际改变完成标准时调用 `guard_scope()`；其中完成标准检查也覆盖已完成任务。
- `app/commitment_service.py` 的 `guard_scope()` 发现该任务所在阶段为 current 且已有承诺版本时，返回 HTTP 409，提示与用户截图完全一致。代码中这条提示仅用于此保护，并非网络错误或普通必填校验。
- `app/routers/start_conditions.py` 的 `change_project_state()` 会在项目正式开始时自动保存任务范围承诺，**没有填写承诺文字也可能存在范围承诺**。因此文字入口显示待补写，不代表标准可以任意更改。
- 页面允许在普通表单中直接修改受保护字段，保存前没有说明后果；出错后只有通用提示，没有携带输入进入调整流程。这是明确的交互衔接缺陷。
- 另有边界缺陷：数据库旧标准 `""` 与表单提交的 `null` 在后端直接比较时不同，可将语义相同的空白误判为变更。

截图无法展示提交前的数据库值或请求体。本次没有读取生产记录，不能断言该次究竟改了标准、阶段，还是遇到旧空字符串边界。截图能确定触发的是以上承诺保护分支；截图中的非空标准使完成标准变更成为主要怀疑，但仍需真实请求差异才能确定该条记录的具体触发字段。「旧客户端请刷新」是通用错误文字，不能据此判定客户端陈旧；真实范围变化不会通过刷新得到解决，未保存文字应先复制保留。

## 合成数据复现

使用项目现有 Python 环境、FastAPI ASGITransport 与 SQLite **内存库**，没有修改依赖或创建业务数据库。

| 操作 | 当前实现的实际结果 |
| --- | --- |
| 未开始时填写完成标准 | 200，可保存 |
| 正式开始但未填承诺文字 | 自动生成范围版本，文字仍为空 |
| 开始后修改普通说明和估时 | 200，可保存 |
| 提交原阶段与相同完成标准 | 200，可保存 |
| 改变完成标准并同时改说明 | 409，整次提交拒绝；重新查库确认说明与标准均未部分写入 |
| 移出当前承诺 | 409，与截图同一提示 |
| 数据库存 NULL、页面提交 NULL | 200，可保存 |
| 数据库存空字符串、页面提交 NULL | 409，错误触发保护 |
| DELETE 阶段地址 | 404，数据库阶段仍存在，当前没有此接口 |

## 保存方案（待确认）

保留有记录的承诺调整和服务端30秒暂停。普通内容直接保存；实际改变完成标准或移出当前承诺时，在原字段附近展示变化提示，主按钮变为「预览承诺调整并保存」。带入新旧值及本次其他输入，不要求重新填写，不静默丢失或部分保存。用户可明确选择「仅保存普通内容」，受保护的输入继续保留并标为待确认。

后果预览展示标准、阶段去向、原预计与已投入、日程、下游依赖、交付及预算影响。暂停或结束运行中的工作片后进入现有服务端暂停机制，填原因后主动确认。确认时重新校验任务、承诺、草稿及关联修订；冲突保留输入并重新核对，禁止把旧预览应用到已变化数据。提交在同一事务中保存本次普通内容、批准的范围变更及新承诺版本。取消不改变数据。

后端与前端均以实际变化为准。兼容 NULL 与空字符串的语义空值；不无差别 trim 非空完成标准，不擅自重写历史快照。不需要为这项空值兼容清洗或删除旧业务数据。为受保护冲突提供明确字段和下一步操作，去掉无依据的「刷新旧客户端」建议。新增回归覆盖：普通编辑、无变化提交、旧空值、真实变更、取消、冲突恢复及事务一致性。

## 本轮承诺收纳方案（待确认）

默认使用紧凑摘要条：左侧「本轮承诺」、明确状态和一行文字摘要；右侧始终保留带文字的按钮。未填为「写下承诺」，草稿为「继续填写」，已确认为「查看 / 调整」，展开时为「收起」。保留箭头方向与键盘焦点反馈，不依赖用户猜测整行是否可点击。

展开后在原位置填写与保存草稿、正式确认，避免跳转或遮挡任务列表。收起只改变显示，不清空输入；未保存输入、已保存草稿、已确认版本明确区分。正式版仍使用服务器草稿与修订校验，不把示例中的页内存储误称为服务端恢复能力。确认后的文字调整走既有承诺版本机制。任务范围、历史收纳到对应展开区域，保留独立入口。

延续纸面底色、宋体任务正文、灰蓝容器和墨蓝操作。铅笔或箭头只辅助文字，不独立承担含义。窄屏重排状态文字，按钮仍可见。示例中折叠条宽屏约76px、窄屏约71—91px；这是示例实测，不能等同正式产品实现结果。

## 阶段真实删除方案（待确认）

用户进一步明确，删除首先用于纠正「阶段写错、建错」。因此以轻量纠错为主场景：只写错名称时提供「修改名称」，保留原阶段身份；多建、建错且没有任务、投入、草稿或承诺等关联记录的空阶段，只展示「删除这个阶段？」的简短确认，点击「删除阶段」即完成，不要求任务去向、调整原因或30秒暂停。正式实现仍由服务器重新检查无关联记录后真正删除数据库行，不能仅依据前端空列表判断；确认前若新增任务或记录，应显示实际变化再核对。

示例中「下一阶段 → 报告与验正」是专用合成错写案例，可尝试改名或直接删除。只有已有任务、投入或历史关联时才展示以下详细处理，不能让普通误建纠错默认承担完整阶段交接流程。正式业务代码仍未授权修改。

本次补充已在浏览器验证：直接改名后阶段及任务归属保留；空阶段删除确认没有任务迁移控件和倒计时；取消后阶段仍在，确认后立即从示例及阶段选项中移除。`05-mistaken-stage-delete.png` 为简短确认截图。示例使用页内合成数据，此验证不代表正式数据库删除已经实现。

每个具体阶段标题旁提供「阶段操作 → 删除阶段」，包括当前、下一和已结束阶段。未分阶段是项目任务分组，不是数据库阶段行，不提供虚假的阶段删除。

删除预览列出阶段名、任务数、已投入时间、草稿与历史数量、任务去向。默认将任务保留到本项目「未分阶段」，也可明确选择本项目其他合法阶段；不跨项目，不移动到已结束阶段。任务身份、完成状态、日程引用、依赖、检查项和工作区间保留。迁入当前承诺时追加范围版本，并预览实际影响。

删除当前阶段时选择接替阶段，或明确选择不设当前阶段、直接推进项目任务；不能擅自把下一阶段设为已完成。接替需复用现有阶段开始条件和前置校验，不能借删除绕开阻塞。涉及未完成承诺的范围改变时先处理去向、原因、后果和服务端30秒暂停；空白草稿及正常完成后的整理不一律强迫等待。没有符合条件的接替阶段时，展示具体原因，保留原数据。

最终确认按钮明确写「删除阶段，保留 N 项任务」，空阶段为「删除这个空阶段」。说明阶段在产品内不能一键撤销；取消保留全部原数据。这里建议不级联删除任务，因为删除组织结构不应顺带抹去真实投入、依赖和交付证据；如要删除任务，应作为单独且明确的操作设计。

### 数据库与兼容边界

当前 `project_tasks.stage_id` 可空，外键已有 SET NULL；但 `stage_commitments`、`stage_commitment_drafts`、`commitment_adjustments` 的阶段外键均不可空，不能只新增 `db.delete(stage)`。

拟采用历史与在用阶段解耦的增量迁移：为相关记录保留项目关联、原阶段 id/标题等身份快照，回填旧数据后允许阶段引用为空，并使用相应外键策略；草稿当前仅关联阶段，还必须补齐项目归属以支持删除后的历史读取。保留原承诺 JSON、原原因和原任务身份，不改写历史内容，不使用整表级联删除。历史查询调整为可读取已删除阶段的脱离记录，并标记「原阶段已删除」。

服务端新增删除预览与确认接口：鉴权和归属校验 → 锁定用户/项目/阶段 → 比对预览版本与实际关联 → 校验任务去向和接替条件 → 同事务迁移任务、保留草稿/历史身份、使旧未确认调整预览失效、记录删除事件 → 执行 `DELETE FROM project_stages WHERE id=...` → 提交。任何环节失败整体回滚。客户端仅在服务器确认成功后移除卡片，失败时保留并显示原因；刷新和其他客户端读取应一致。

迁移必须分别验证 SQLite 与生产 PostgreSQL 外键行为、幂等性和历史数据保存，不能只依赖 SQLAlchemy 模型声明。验收还需包含：空阶段、含任务阶段、当前与最后阶段、已结束阶段、越权、并发更新、目标阶段被删、工作片运行中、旧预览失效、数据库查询确认阶段行不存在、任务与投入仍在，以及刷新/跨客户端一致性。这些正式实现验证尚未执行。
