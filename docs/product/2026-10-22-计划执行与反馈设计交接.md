## 1. 先明确交接范围

本次目标是帮助用户通过真实使用，逐渐学会估计时间、开始行动、面对困难、判断重要性以及制定更长周期的计划。只有字段、提示文字或统计数字，不能算实现了能力训练。

完整过程是：

**明确目标与可行性 → 检查启动条件 → 安排当前阶段与当天任务 → 再次审视重要性 → 预演并开始 → 反馈实际投入与结果 → 每日和周期复盘 → 调整下一阶段。**

本文件保留用户原始七项编号，第1项同时包含估时反馈和心理建设；新增的启动条件与约束独立编号为第8项。不得只实施后续补充，遗漏原来的要求。

本次交付仅整理设计文档，不修改业务代码、不迁移数据、不发布安装包、不执行生产部署。后续实施仍须遵守仓库 `AGENTS.md` 与 `docs/ops/协作手册.md`。

### 1.1 要求与设计的状态

- **用户明确要求**：原始七项的目标与具体要求；任务和项目开始前的条件、依赖与约束；调整当前列表时说明后果、强调严格执行的重要性；通过强制等待给用户暂停思考的机会。
- **用户明确接受的取舍**：下一阶段允许提前收集想法；切换前先处理当前阶段未完成项；条件变化时允许说明原因并调整，采用这一规则仍必须提醒调整后果。
- **本稿采用的设计默认值**：等待30秒；后果说明可见时累计，后台暂停，刷新恢复；正常任务轮转、暂停和休息不触发；结构化预演、分级启动条件以及具体布局等细节，属于根据讨论汇总的设计方案。
- **后续实施需核对的内容**：数据结构、接口拆分、旧客户端兼容方式与具体技术实现。不得把设计默认值声称为用户逐字段确认过的要求；重要取舍变化先说明。

## 3. 概念边界

| 概念 | 回答的问题 | 不能混用的内容 |
|---|---|---|
| 目标 | 希望达成什么结果 | 目标存在不代表目标现实可行 |
| 项目 | 围绕哪个可交付结果组织工作 | 创建项目不等于满足条件、正式开始 |
| 阶段列表 | 当前承诺推进哪些任务，后续任务放在哪里 | 下一阶段不是“记”里的宽松收集箱 |
| 每日日程 | 今天安排哪些任务、投入多少时间 | 日期先后和列表顺序不能冒充依赖 |
| 重要性 | 完成任务对当时目标有多大帮助 | 不等于旧优先级，也不等于是否有趣 |
| 简单／困难 | 相对于当前能力，执行的难度如何 | 不等于熟悉／陌生，也不等于重要／不重要 |
| 启动条件 | 开始前是否具备必要条件 | 不等于完成检查项或验收标准 |
| 执行约束 | 执行期间必须遵守哪些边界 | 不一定只在开始那一刻有效 |
| 任务步骤 | 按什么顺序做 | 不等于哪些任务必须先完成 |
| 检查列表 | 准备或交付时有哪些事项需要核对 | 勾完检查项不自动代表结果合格 |
| 验收标准 | 什么可观察结果算完成 | 不等于用了多少时间 |
| 用时反馈 | 最初估计与实际完成投入有什么差异 | 不把尚未完成的当前投入当最终实耗 |

补充原则：

- “未标记”“未反馈”“未记录”“未确认”都需要独立表达，不能默认为不重要、没做或失败。
- 先执行当前承诺，不等于同一阶段内不能合理轮转任务或休息。
- 鼓励直面困难，也不等于把所有未完成都归因于逃避；可能存在资源、健康、估时或目标问题。
- 严格执行与理性调整同时成立：调整必须有后果说明、暂停机会、原因与历史记录。

## 4. 页面职责与完整使用过程

### 4.1 页面职责

- **日程**：当天目标、任务安排、估时、难度与重要性标记、二次审视、开始入口和当天反馈。普通事项也能走完整流程，不强制先建项目。
- **项目**：目标可行性、项目启动条件、阶段承诺、任务依赖、预演、检查与验收、计划周期练习。
- **记**：时刻、idea、以后想做；补全实际活动及事后评价。已有内容可被明确关联和引用，不自动变成工作实耗或项目阶段任务。
- **日报／周报**：统一呈现已记录投入、估时反馈、困难部分进展、实际目标帮助、有趣但无助于目标的活动、调整及下一步。避免再建一个彼此重复的报告入口。
- **现有长期目标页**：保留活动与消费记录职责。计划练习建议在项目内承接，相关报告可关联展示，不能把活动统计改个标题就当作计划训练。

### 4.2 当天安排与执行

1. 明确今天希望推进的目标；可以使用已有目标或简短描述，不强迫建立大型项目。
2. 添加任务，估计用时，标记简单／困难及三级重要性。快速记录允许稍后补充。
3. 汇总预计投入，结合可用时间检查是否过载；没有可用时间依据时只展示估计，不假装知道用户当天容量。
4. 完成初步安排后，进入重要性再次审视；可修改或明确确认保持原标记。
5. 开始前展示相关启动条件，提供预演及“有点难开始”的支持入口。
6. 执行并记录工作片；也可事后反馈。必要条件未满足时按第12节处理。
7. 完成或结束当天工作后，核对实际投入、结果与偏差；允许暂缓反馈，并在日报中保留待反馈状态。
8. 日报回看困难部分、有趣但无助于目标的活动及需要调整的下一步。

### 4.3 阶段推进与计划练习

1. 检查目标可行性与项目启动条件，先完成必要筹备。
2. 形成当前阶段任务列表，明确这一轮要交付的结果。
3. 正式开始时确认执行承诺；后续想法放入独立的下一阶段列表。
4. 当前阶段内按真实依赖选择可执行任务；允许正常任务轮转和休息。
5. 若需提前调整，先展示后果并完成30秒暂停，再处理未完成项及原因。
6. 正常交接或有记录地调整后，下一阶段成为当前阶段，同时保留旧阶段历史并建立新的下一阶段列表。
7. 周期结束时对照计划与现实，决定下一轮内容和适合的计划跨度。

## 5. R1：估时反馈与开始行动的心理建设

### 5.1 专门的用时反馈

日程任务直接展示“预计用时／已记录投入”。任务完成时提供明确的“用时反馈”区域，普通日程与项目任务均可使用：

- 原来预计多久；如有修订，同时展示当前估计。
- 实际完成用了多久；优先带入有效工作片，允许用户核对、更正或直接反馈分钟数。
- 差额和方向：比原估计多用或少用多少时间。
- 偏差原因：漏算步骤、任务陌生、返工、范围变化、打断等，可补充说明。
- 下次类似任务准备怎样估计；需要补充哪些步骤或余量。
- 反馈依据与确认状态：计时核对、手工补记、自报总量、待核对等。

示例：原估计30分钟，反馈确认实际45分钟，显示“比预计多15分钟”；原估计大于0且数据可比时，可补充“多50%”。原估计缺失或为0时不计算比例。

完成、部分完成、需要返工分别记录。部分完成显示“目前已投入，尚未完成”，不纳入最终完成任务的估时准确性结论。因范围变化产生的差异要单列，不能直接判定用户估时能力差。

### 5.2 反馈用时与时间账的统一口径

必须支持不一直开计时器的用户，同时防止一份投入重复相加：

1. 工作片、明确区间的补记，构成可分配到日期和时间轴的记录投入；暂停和休息不算工作投入。
2. 任务反馈中的最终确认值默认带入已记录工作投入。已有工作片时，不能再把用户填写的总时长当作一份额外工作片相加。
3. 用户只记得总分钟数、没有起止区间时，允许保存“自报完成用时”，用于本次估时反馈；不得伪造起止时刻或与已有片段重复计入自然时间。
4. 自报总量与工作片不同，界面明确展示两者及差异，并让用户核对。用于本次估时对照的最终确认值只有一个，保留来源和更正记录。
5. 日报按真实区间汇总投入。尚未分配到具体区间的自报总量另列说明，不能把整个任务跨日总量塞进完成当天，也不能隐瞒它尚未进入时间账。
6. 要更正每日时间账，用户可补齐或更正具体区间；重复、重叠、跨天区间按统一规则检查。

这一区分是实现建议，目的在于同时满足“直接反馈实际用时”与“不重复记时”。最终实现不得悄悄取消任一能力。

### 5.3 原估计与下一次学习

- 项目任务已有原估计和当前估计，继续保留，并补足修订历史；普通日程也应具有同等能力。
- 后续修改不能覆盖最初估计。执行后才补填的数值明确标为补填，不能伪装成事前预测。
- 日报呈现本次对照，周报观察重复出现的偏差并显示样本数量、缺失数据和范围变化情况。
- 再次估时允许找回用户明确关联的相似任务经验；不要直接替用户填好答案。相似性不可靠时由用户选择，不能凭标题相近断言可比。
- 不给用户打羞辱性分数，不凭少量记录声称已经形成稳定趋势。

### 5.4 心理建设必须接到行动

在开始入口旁提供用户主动打开的“有点难开始”，可选择当前顾虑：担心做不好、害怕评价、事情太大、准备不清楚、已经开始晚了等。

| 用户情境 | 支持内容方向 | 紧接着的行动 |
|---|---|---|
| 怕做错、做不好 | 遇到问题是执行中的常见过程，可以先做小结果再检查和修改 | 写下一个可检查的小结果，开始短工作片 |
| 过分在意外部评价 | 先明确完成标准，区分有助改进的意见与无建设性的否定 | 查看标准，写下下一步 |
| 事情太大或不清楚 | 缩小到现在能开始的一步，先获得事实 | 简短预演、准备材料或做探索任务 |
| 已经开始晚了 | 检查剩余时间能交付什么，再立即做这一部分 | 调整本次范围并开始 |
| 遇到挫折 | 看清具体问题，从尝试中吸取经验并调整方法 | 记录卡点、拆分下一步或寻求帮助 |

提示简短、可收起，避免频繁弹窗。不得把“恐惧是唯一原因”“未完成就是逃避”作为系统诊断，也不用夸张倒计时制造紧迫感。软件提供支持与开始入口，不声称治疗心理问题。

## 6. R2：简单／困难与直面困难反馈

- 日程与项目任务提供独立的“简单／困难”标记，允许未标记；保留熟悉程度时必须另列。
- 难度相对于用户当前能力，不强制把重要任务判为困难，也不自动认为困难任务都值得优先做。
- 同一任务包含两类部分时，可拆成子任务分别标记，必要时单独记录困难部分投入。父子任务汇总不得重复计算。
- 安排当天任务时提醒：是否只安排了容易部分；重要且困难的部分是否有明确的下一步与可用时段。鼓励较快处理简单部分，为困难部分保留投入。
- 日报单列困难部分的实际时间、已推进内容、已解决问题、阻碍与下一步，不只给完成率。
- 统计依据采用记录时的难度或可追溯快照。后来改标记，不能暗中改写历史日报含义。

反馈示例：“今天在困难部分投入25分钟，完成资料核对，论证仍待处理。下一步先列出两条证据。”

连续没有进展时，先核对是否漏记以及实际原因，再提供缩小步骤、补充条件、寻求帮助、调整时间或目标等选择。未记录不等于没做；合理调整不等于失败。困难反馈及心理提示可收起或减少，不使用红色失败提醒、连续失败天数或强迫继续的通知。

## 7. R3：三级重要性、再次审视与有趣但无助于目标的活动

### 7.1 统一标记与判断依据

新的任务重要性使用且只使用三级：**不重要／一般／重要**。未标记是空值，不是第四级。

判断依据明确展示：

> 判断一项任务是否重要的标准：完成这项任务，是否确实有益于达成目标？

首次标记后，在完成当天初步安排时出现“审视重要性”环节，展示当时目标、全部任务及第一次标记。既检查显得重要的，也检查显得不重要的；用户可修改，或明确确认维持原判断。后续新增任务可以补审，不必每点击一次标签就弹窗。

快速收集可以稍后审视，但需要可见的待审视状态，不能把二次审视藏在用户找不到的入口里。

### 7.2 计划判断与实际判断分开

- 计划标记回答“预计对目标有什么帮助”。
- 实际评价回答“实际做的事情对当时目标有什么帮助”。
- 保留初次标记、再次审视结果、目标与文字快照及时间，允许复盘两种判断的差异。
- 目标改名不追改历史评价；系统不自动从日程标签推导实际活动评价。
- 休息、健康和陪伴都可能服务于用户目标，由用户判断，不自动判为无用。
- 旧优先级与新的目标相对重要性语义不同，不能直接把0／1／2改名迁移，迁移见第14节。

### 7.3 每日反馈

明确询问：“今天有没有做过有趣，但无助于当时目标的事？”允许回答有、没有、暂不确定或稍后反馈。

有时可以记录事情、实际时间、当时目标、原因及下次打算。已有实际活动评价可引用，不要求重填。是否有趣与重要性分别存储，未判断不能当作“没有”。

日报展示用户明确判断的活动及时间，并说明未记录、未判断部分。与现有注意力浪费、非计划占用保持关联但不直接相加；同一段时间只累计一次，也不把所有有趣活动都判为浪费。

## 8. R4：目标现实可行性

新建或显著调整目标／计划时，明确呈现：

> 计划成功的前提是目标现实可行。
>
> - 已经有人做到了。
> - 我与那个人没有太大的差距。

提供可逐步补充的简短检查：参考谁、对方用了多久和什么方法、自己的起点与资源如何、差距在哪里、怎样弥补、当前期限是否足够。

别人做到过不意味着自己一定能在当前期限内做到，不能由两个勾选项自动宣布可行。缺少案例或尚不了解任务时，允许先建立探索步骤，获得事实后重新评估；不能禁止所有探索性目标。

执行中发现目标、资源或期限不现实，可以调整，保留依据、前后版本及原因。相关调整若改变已开始的当前列表，仍执行第11节的后果预览和暂停规则。

## 9. R5：长期计划能力练习

在项目中提供计划周期练习。初次建议从一周开始，也可按用户情况选择；之后可尝试两周、一个月、一个季度、一年。周期是选择，不做打卡解锁，不强迫年度规划，也不规定每个人必须沿同一速度升级。

每轮至少具有：起止日期、预期可检验结果、当前任务范围、预计投入与可用时间、关联目标、执行记录、周期复盘、下一轮调整。

周期结束时对照：

1. 原来希望达成什么，实际得到了什么结果。
2. 原来安排多少任务、估计多少投入，实际用了多少时间。
3. 哪些困难、依赖和变化没有预见；哪些条件判断不成立。
4. 哪些工作确实推进了目标，哪些只是显得忙碌。
5. 下一轮调整内容、方法、负荷，还是计划跨度。

建议必须说明依据。完成率只是参考之一，不能用它单独评判计划能力；用户可以选择维持、缩短或延长期限。不把理性停止不可行目标视为失败，也不把不断缩减目标自动夸为进步。

简单事项仍可直接安排、直接开始。陌生事项可先做探索片积累认识，再制定更有效的计划。预演、可行性填写及规划不应成为所有行动的前置长表单。

## 10. R6：可实际使用的任务预演

日程及项目任务均有明确的“开始前预演”入口。建议采用四个短问题：

1. 第一步是什么，接下来按什么顺序做？
2. 需要准备哪些材料、工具或条件？
3. 最可能卡在哪里？
4. 如果卡住，准备怎样应对？

允许只填需要的内容或直接开始；已有硬性启动条件仍需满足，跳过预演不能绕过条件。

保存后，在执行区域显示第一步、关键准备和应对方法。用户明确选择后，准备事项可以生成独立检查项或筹备任务；文字提到某件事不自动创建依赖，也不自动勾选完成。

结束后可回看“哪里与预想不同”，将经验用于下一次。已有 `rehearsal_note` 原文完整保留并可见，不自动推断为用户确认的结构化答案。

## 11. R7：阶段列表、执行承诺、调整暂停与任务检查列表

### 11.1 当前与下一阶段

- 每个项目有明确的当前阶段及独立的下一阶段任务列表。阶段按项目推进划分，日程显示任务归属并安排当前阶段工作。
- 后续想法可以提前收集到下一阶段，不自动混入当前列表或执行队列。“记”的以后想做继续作为尚未纳入项目的收集箱。
- 形成并正式开始当前列表时，记录本轮承诺的任务范围和交付结果。没有开始的草稿可正常编辑，不对整理草稿施加30秒等待。
- 当前阶段内允许按依赖和实际情况交替处理可执行任务，保留时间片轮转能力。
- 完成当前列表后正常交接：核对结果，下一阶段转为当前，保留旧阶段，建立新的下一阶段列表。
- 条件变化时允许调整，但不能把旧阶段无说明地丢回下一阶段，也不能把取消、转移或部分完成伪装成完成。

### 11.2 必须告知严格执行的重要性

在列表正式开始时明确展示，在调整前再次提醒：

> 当前列表是本阶段的执行承诺。严格执行有助于集中投入、完成关键工作，并检验原先的计划是否合理。后续想法先放入下一阶段，避免不断打断当前任务。

不能只说“可以灵活调整”而略去承诺和坚持。也不能用羞辱、失败标签或恐吓文案代替解释。

### 11.3 调整前说明本次具体后果

用户移出未完成的承诺任务、缩减已开始的范围、提前结束阶段或提前切换下一阶段时，先展示：

- 尚未完成的任务，以及每项准备延期、转移、取消还是继续保留。
- 受影响的任务、项目及其依赖关系，哪些仍无法开始。
- 原定交付结果是否将不完整，哪些验收内容受到影响。
- 对既定日期、预计工作量和时间预算的已知影响；无法可靠推算时明确说明需要重新估计，不能编造确定延误天数。
- 已投入时间与已有结果仍保留，转移或结束不会把未完成变成完成。

提醒频繁调整可能造成重新进入任务的成本，并可能让重要但困难的工作持续被推迟；同时允许用户说明真实条件变化，不代替用户判定动机。

### 11.4 强制30秒暂停

目的：在改变执行承诺前给用户一个暂停机会。30秒提供机会，不能证明用户实际认真思考。

规则：

1. 完整展示本次影响后开始累计30秒；不是用户进入项目页面就提前计时。
2. 显示具体后果、严格执行提醒与问题：“这次调整是因为条件确实变化，还是因为当前任务遇到了困难？”
3. 等待时可填写调整原因、逐项处理未完成事项。“确认调整”禁用并展示剩余秒数。
4. “继续当前列表”始终可立即点击，默认突出；返回原任务、暂停计时或休息不必等完。
5. 只在后果说明处于可见前台时累计；切到后台或离开说明时暂停，返回继续。
6. 刷新、重新打开不能绕过等待，也不应无故把同一次已累计的时间清零。
7. 累计满30秒、填写必要原因且未完成项处理完整后，允许点击确认；不自动切换。
8. 同一次调整绑定用户、项目、当前阶段版本及影响方案。重复提交不重复切换；不同页面不能并行加速累计。
9. 等待期间方案或相关依赖发生实质变化，重新展示影响；新方案重新等待。未变化的同一方案刷新恢复。
10. 计时状态与确认资格需服务端配合核验，不能只依赖本地按钮或 `setTimeout`；具体协议由实施者设计并验证，前台可见状态只能作为交互信号，不能声称证明注意力。
11. 等待不计入任何任务工作时长。如果当时有工作计时，先让用户明确暂停或结束并正确结算，不允许思考等待被动增加任务实耗。

触发边界：

| 操作 | 是否等待30秒 |
|---|---|
| 当前承诺尚未完成，提前切换或结束阶段 | 是 |
| 从已开始的当前承诺中移出未完成任务、缩减交付范围 | 是；允许合并为一次完整调整 |
| 通过日程、项目、其他入口实现同样的提前调整 | 是，入口不能绕过规则 |
| 当前列表全部完成后的正常交接 | 否；仍展示交接结果并检查下一阶段条件 |
| 同一阶段内正常任务轮转、暂停、休息 | 否 |
| 向下一阶段收集想法、编辑尚未开始的草稿 | 否 |
| 只修改文字或当天安排，未改变阶段承诺 | 否；如实际转移承诺范围则按调整处理 |

### 11.5 调整后的记录

记录调整前后范围、后果快照、原因、每个未完成项去向、等待确认状态和时间。当前阶段的承诺、任务身份、历史时间、结果与依赖都应可追溯。

日报及阶段复盘可以呈现发生了什么调整及后续安排，不做连续失败惩罚。30秒结束不代表依赖已满足，也不赋予用户绕过硬性条件的资格。

### 11.6 任务检查列表

阶段任务列表、步骤、检查项和验收标准分区呈现。任务检查项支持新增、编辑、排序、勾选及明确标为不适用，并可从已有流程复用；已有勾选状态原样保留。

开始前准备检查与交付前核对可按用途分组。要限制开始的准备事项，应明确设置为第12节的硬性启动条件，不能依赖一个普通复选框暗中拦截。

标记完成时展示未核对项，允许补查，或在说明不适用／例外后确认，保留记录；不把所有普通检查项都强制升级成硬条件。流程模板修改不追改已经生成的任务实例。

## 12. R8：项目和任务开始前的依赖、条件及约束

### 12.1 必须同时覆盖项目级与任务级

- 项目级：正式开始项目需要满足的条件，作用于项目的正式执行任务。
- 任务级：开始某个任务自身需要满足的条件。
- 普通日程事项也应有轻量入口，不要求先转换成项目才能记录自己的开始条件。
- 项目可以先创建和筹备，再正式开始。筹备活动需要明确身份与作用范围，不能因项目未启动把补齐条件的工作本身锁住，也不能把所有正式任务默认当筹备以绕过条件。
- 子任务的继承范围需要界面可见；只属于某一步的条件不应误封锁其他独立准备工作。

### 12.2 条件类型及判断方式

| 类型 | 示例 | 判断与操作 |
|---|---|---|
| 前置任务 | 先完成资料核对，再写正文 | 关联具体任务及所需完成／验收状态，系统判断 |
| 前置项目 | 项目A交付验收后，项目B才能启动 | 关联具体项目及所需状态，系统判断；不能只看项目是否存在 |
| 材料与资源 | 文件齐全、设备或场地可用 | 用户确认并可记录依据，不根据备注自动视为具备 |
| 外部条件 | 收到许可、确认、回复或交付物 | 用户确认状态，可关联证明或说明，不擅自发消息索取 |
| 时间条件 | 指定日期后开始、需要连续一小时 | 可计算日期由系统检查；可用连续时段不能凭空推断 |
| 执行约束 | 预算上限、指定资料或特定执行要求 | 明确作用范围与检查时机；有可靠数据才自动判断，否则人工核对 |

条件可逐步补充，不为每个简单事项强制填写全部类型。无配置时显示“未配置启动条件”；不能声称已经核实所有现实条件。

### 12.3 必须满足与提醒事项

- **必须满足**：未满足或尚未确认时，不允许开始依赖该条件的正式工作，显示原因、条件来源和补齐入口。
- **提醒事项**：开始前展示，用户了解影响后可继续；需要时记录说明。
- 自动可判断的依赖不能通过手动勾选伪造完成。外部条件支持未确认、未满足、已满足、不适用；不适用需要说明，不能偷偷清除硬性要求。
- 改变或撤销一个已经生效的必要条件，应明确说明影响并保留原因。若同时改变当前执行承诺，进入第11节流程，不能提供无记录的“仍然开始”绕过硬条件。
- 截止日期超过后通常应提示交付影响、调整范围，不能一律禁止行动。未到允许开始日期与已经错过截止日期要分别处理。

### 12.4 统一检查的入口

项目与任务详情各有独立的“开始条件与约束”区域。卡片或任务行显示“可以开始”“等待文件确认”“等待项目A验收”等具体原因。

| 入口或行为 | 检查要求 |
|---|---|
| 正式开始项目 | 检查项目条件并记录启动判断 |
| 加入执行队列 | 显示可执行状态及阻碍；未满足项可保留为明确受阻候选，但不能作为可开始队首 |
| 开始、切换或恢复任务 | 再检查项目级及任务级相关条件，不能只相信页面旧状态 |
| 提前切换阶段 | 同时检查当前调整资格和目标阶段条件，30秒不能代替依赖检查 |
| 标记完成与验收 | 检查有关交付约束，不用勾选完成回避受阻状态 |
| 事后补记 | 如记录时条件未满足，保留实际发生的事实与说明，不能用当前门槛抹去真实历史 |

### 12.5 依赖图及状态变化

- 保留现有同项目任务依赖，增量扩展项目关系和其他条件。引用必须属于同一用户，禁止跨用户泄露或关联。
- 跨项目任务关系如用于表达明确前置，应在统一依赖模型中校验；不得简单删除现有“同项目”校验而失去权限、环和历史保护。
- 禁止自依赖、重复关系和循环；项目与任务继承形成的混合关系也要检查，避免项目A等待项目B、项目B又间接等待A。
- 前置项取消、移除或重新打开，不自动视为满足；提示受影响对象并要求重新处理。
- 已经开始后条件失效，提示具体影响，让用户明确选择暂停、补齐或调整。不得删除真实工作记录或凭空自动声称可以继续。
- 修改条件或前置关系后的可执行状态，在日程、项目及队列中保持一致。

## 13. 统一日报、周报与统计规则

日报在现有报告入口承接下列区块，可折叠详情，避免一次展示冗长表单：

1. **实际投入与结果**：当天工作时间、完成／部分完成／返工结果，已记录与待核对范围。
2. **估时反馈**：本日完成任务的原估计、最终确认实耗及偏差原因；跨日任务标明累计口径，不把全部时间计入今天。
3. **困难部分**：投入、推进内容、阻碍及下一步，不只显示完成率。
4. **目标与重要性**：实际活动的三级判断、未判断部分、计划与实际差异。
5. **有趣但无助于目标**：用户的明确判断、相关活动及时间，区分没有、未答和不确定。
6. **调整记录**：发生了什么范围或阶段调整、原因与后续去向。
7. **下一步**：用户选择的一个可执行行动；预演和条件问题可直接引用。

周报再呈现多日经验、反复偏差与本轮计划复盘。长期分析遵守现有权益，不在本轮擅自改变收费边界：记录、计时、日报、周报和本人数据导出继续可用；项目目标创建继续免费，现有付费长周期深度复盘按原规则执行。

统一口径：

- 自然时间不重复累计；工作片跨北京时间日期边界裁切，暂停和休息与工作分开。
- 项目任务与关联日程共用稳定身份；同一任务跨天安排不多建一份反馈或把累计实耗重复求和。
- 难度、重要性、目标和范围采用当时的可追溯判断；不暗中以今天的标签重算历史意义。
- 只有具备有效估计、完成结果和已确认实际用时的可比样本才进入估时趋势；未填、补填、未完成、范围变化分别说明。
- 各区块可以引用同一活动，但时间总账只计算一次；“有趣但无助于目标”“非计划占用”“注意力浪费”不直接叠加。
- 不把记录缺失当作0，不把少量样本和用户自报包装成客观能力诊断。

## 14. 数据、兼容与迁移

### 14.1 建议的增量记录

以下是逻辑记录，不强制一项一张表；物理结构在实施时核对现有模型后决定。

| 记录 | 关键内容 | 与现有数据的关系 |
|---|---|---|

### 14.2 兼容和保护

- 业务数据默认保存在服务器。只做必要的增量迁移；本地检查使用内存数据库或专用测试数据，不在C盘建立业务数据库。
- `ensure_schema()` 保持幂等；生产PostgreSQL迁移需事务、索引与失败回滚检查，旧库升级验证保留用户记录。
- 不删除、清空或批量改写用户历史，不清理Docker卷，不把本轮设计与旧板块数据清理混在一起。
- 旧priority、熟悉程度、时间日志间隔、相邻并行分组分别保留，不能自动转换为新重要性、难度、真实工作区间或依赖。
- 对旧优先级建议明确保留“旧优先级”来源，新重要性保持待审视；不把没有选择的用户默认标为不重要。
- 旧项目没有配置条件时保留既有事实与可用性，展示条件未配置；不批量变成受阻项目，也不伪造“已检查通过”。
- 旧任务无事前估计、无历史难度或无正式开始时间时，保持未知；不能用迁移时间补成用户过去的判断。
- 旧客户端缺少新字段时不清空现有数据。涉及实际门槛的旧接口同样服务端检查，并返回可理解的升级或处理指引。
- 已保存反馈、调整和依赖历史需要纳入本人导出与备份；任务移除不得级联删除工作片或历史判断。
- 模板生成的是独立实例，修改模板不改旧任务；删除前置对象也不能暗中解除所有历史约束。

## 17. 逐项验收清单

以下均为后续实施验收项，当前不勾选。至少覆盖普通日程、关联项目任务、跨日记录、刷新恢复和不同入口的一致性。

### A1：估时与实际反馈

- [ ] 普通任务预计30分钟，反馈45分钟，显示多15分钟；原估计不被修改覆盖。
- [ ] 已记录20分钟、最终确认30分钟时，不合计成50分钟；自报与区间口径清楚。
- [ ] 没有计时的用户可以直接反馈实际用时，来源明确，不伪造时间轴。
- [ ] 部分完成、返工、补填估计、范围变化、缺失或0估计得到不同且正确的处理。
- [ ] 跨日任务保留累计反馈，日报只累计当天真实区间；下一次可以找回相关经验。

### A2：心理建设与行动

- [ ] 害怕做不好、在意评价、任务不清楚、起步晚等情境有对应简短支持及行动入口。
- [ ] 用户可以直接采取一个小行动，也可以关闭提示；不被要求先完成心理问卷。
- [ ] 未完成不会被系统自动归因为恐惧、懒惰或逃避。

### A3：困难部分

- [ ] 简单／困难与熟悉／陌生、重要性分开；可以标记任务中的困难部分。
- [ ] 困难任务未完成但有投入与进展时，日报如实体现，不只给低完成率。
- [ ] 未记录与确认没做区分，反复停滞提供具体调整帮助，可减少提示。
- [ ] 改变今天的难度标签不暗中改写过去记录，父子任务时间不重复。

### A4：三级标记与再次审视

- [ ] 新标记只有不重要／一般／重要，未标记为空；旧优先级没有被直接改名。
- [ ] 首次标记后有可见再次审视，包含全部任务，可调整或确认保持。
- [ ] 目标收益判据明确，目标及初次／再次判断可追溯；普通事项也能参与。

### A5：每日实际评价

- [ ] 计划重要性不自动变成实际评价，目标改名不修改历史依据。
- [ ] 每日明确记录是否做了有趣但无助于当时目标的事，区分有／没有／不确定／未答。
- [ ] 可引用已有活动，不重复填写或重复累计注意力浪费等时间；不自动贬低休息与陪伴。

### A6：可行性

- [ ] 目标现实可行提醒及用户指定的两条标准完整出现。
- [ ] 能记录方法、耗时、起点、资源差距与弥补方式，并在行动后修订。
- [ ] 缺少案例可先探索，两个勾选项不会被系统宣布为成功保证。

### A7：长期计划练习

- [ ] 能完整经历短周期制定、执行、结果对照、复盘及下一轮决定。
- [ ] 可选一周、两周、一个月、季度、年度等跨度，可维持、缩短或延长，无打卡解锁。
- [ ] 建议有依据，不只依赖完成率；简单或陌生任务仍可先行动。

### A8：预演

- [ ] 日程和项目均能找到入口，四个问题能保存，执行时能看到第一步与准备。
- [ ] 用户可选择把准备变为检查项或筹备任务，不自动创建未经确认的依赖。
- [ ] 能对照实际执行，旧预演笔记保留；跳过预演不绕过硬性启动条件。

### A9：阶段列表与严格执行

- [ ] 当前与下一阶段独立，后续想法不自动挤入当前执行；以后想做不混为下一阶段。
- [ ] 正式开始和调整前都说明严格执行的重要性。
- [ ] 提前调整逐项展示未完成内容、依赖影响、交付变化及时间预算的不确定性。
- [ ] 正常交接与有原因调整均保留历史，取消或转移不自动算完成。

### A10：30秒暂停

- [ ] 后果说明显示后才计时，30秒前无法确认；等待期间可填写原因和处理去向。
- [ ] 后台暂停，返回继续；刷新恢复；同一调整多页面不加速，直接请求不能跳过门槛。
- [ ] 等满仍需用户点击，原因与未完成项不完整不能提交；重复请求只生效一次。
- [ ] 影响方案发生实质变化重新展示并等待，未变化刷新不无故清零。
- [ ] 继续当前列表随时可用；普通任务轮转、暂停、休息、草稿编辑和正常交接不强制等待。
- [ ] 等待不进入工作实耗，且30秒通过不会解除下一阶段未满足的硬性条件。

### A11：检查列表

- [ ] 检查项可增改、排序、勾选和说明不适用；与步骤、前置及验收标准分开。
- [ ] 完成时展示未核对项并保留处理记录，不把普通检查项暗中变成硬门槛。
- [ ] 旧勾选状态保留，模板更改不修改历史实例。

### A12：项目与任务启动条件

- [ ] 项目、项目任务及普通日程可以记录适用条件；创建、筹备和正式启动有区别。
- [ ] 项目A满足指定交付状态后项目B才可启动；条件来源、阻碍与解决入口可见。
- [ ] 材料、外部确认、时间及执行约束可表示，必须满足和提醒事项分别处理。
- [ ] 前置筹备不被项目条件锁死，其他独立工作不被无关条件误封锁。

### A13：依赖一致性

- [ ] 拒绝自依赖、重复边、跨用户引用和包含项目／任务继承的循环。
- [ ] 开始、切换、恢复及日程入口统一检查，旧客户端也不能绕过实际门槛。
- [ ] 前置取消、移除、重新打开或条件失效会反馈影响，不自动当作满足。
- [ ] 已经发生的实际工作可以补记并说明，不因当前条件而被删除或禁止记录。

### A14：兼容、历史与完整交付

- [ ] 增量迁移可重复执行，旧记录、原始估计、检查项、依赖、预演笔记与工作片保留。
- [ ] 新增历史可导出及备份，无业务数据库落在C盘，无用户数据清理。
- [ ] 记录缺失不被当0或失败，各报告时间不重复，既有权益和无关模块不受本轮擅自改变。
- [ ] 八项需求都有实现与验证证据，未完成项明确列出，不能只凭字段或说明宣称完成。
