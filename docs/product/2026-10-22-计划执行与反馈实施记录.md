### 实际实现

1. 项目、项目任务及普通日程都可配置独立的开始条件与约束：前置任务、前置项目、材料资源、外部条件、允许开始时间、需要人工核对的连续时段及执行约束。
2. 条件区分必须满足与提醒事项，以及开始前、执行期间、交付前的检查时机。硬条件未满足或未确认时拦截实际执行；提醒事项开始前需明确确认。人工确认有依据，不适用需说明；自动判断的依赖和日期不能用手动勾选伪造。
3. 新项目明确从筹备状态开始，正式任务继承项目条件；创建任务时可明确指定筹备用途，只检查该任务自身条件。筹备任务不会被项目启动条件锁死，普通子任务也不会继承不属于自己的父任务条件。
4. 项目正式开始时保留启动时间及检查快照。按正式开始、交付、验收记录状态与原因；有未完成任务不能声明交付。重新打开已交付任务需说明原因，项目回到执行状态，相关后续依赖重新受阻。交付后条件变化时也能明确重新筹备，避免缺条件又无法筹备的死锁；首次启动时间与历史保留。
5. 开始、切换、恢复、项目任务验收及普通日程完成均接入服务端检查。切换使用原子接口，目标受阻时保留原工作片。队列和日程显示具体受阻原因；条件失效时执行区提示用户暂停、补齐或调整，不删除真实工作。
6. 新条件支持跨项目任务前置和项目交付／验收依赖。旧同项目任务依赖继续保留；两种模型共同检查自依赖、重复关系、跨用户引用及项目启动／交付／任务继承形成的混合循环。前置移除或重新打开不算满足。
7. 条件变更、移除、原有依赖增删和项目状态变化均保留历史及原因。移除条件采用软删除；日程纳入项目后继续使用原条件及历史，不另造一份任务时间。
8. 事后补记仍允许保存已发生的工作：当前受阻时需说明当时情况，保留实际区间。当前门槛不删除历史，也不把补记当作实时开始。
9. 增量迁移可重复执行；旧项目正式启动状态与时间保持未知，未配置条件时继续可用。原估计、当前估计、旧预演、检查项、依赖及工作片保留；不把旧priority或熟悉程度改为新语义。新增条件与历史纳入本人导出、逻辑备份。

### 界面使用

- 项目页“当前项目”中查看执行状态、填写判断依据并正式开始；下方独立展开项目条件。
- 添加任务时在“补充估时、任务用途与完成标准”中明确是否为筹备任务。默认正式任务，继承项目条件；任务用途在本批通过创建入口指定，不提供无记录的批量改标绕过入口。
- 任务详情的“开始条件与约束”“完成检查”“安排与验收”分别承担前置核对、普通检查和结果核对。旧预演仍保留，不把它声称为结构化预演已完成。
- 普通日程任务有“开始条件与约束”按钮，通过独立对话框管理；无需先纳入项目。旧优先级暂保持原样，其语义迁移在R3批次完成。
- 允许开始时间按用户输入时区转换为UTC保存；界面使用明确时区的提示。连续可用时段与预算没有可靠数据时由用户确认，不凭预计分钟自动判定。

## 用户执行生产更新

本批有增量数据库迁移。先备份并验证备份目录，再更新源码和构建。以下命令不删除数据库、Docker卷或旧安装包。

Windows PowerShell登录：

```powershell
ssh ubuntu@43.161.238.165
```

登录Ubuntu后执行：

```bash
sudo -i
set -e
cd /opt/shuran-app/deploy/aliyun
install -d -m 700 /root/shuran-backups
backup_file="/root/shuran-backups/pre-2.0.18-$(date +%Y%m%d-%H%M%S).dump"
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_file"
test -s "$backup_file"
docker compose exec -T db pg_restore --list < "$backup_file" > "$backup_file.list"
test -s "$backup_file.list"
cd /opt/shuran-app
git pull --ff-only origin main
cd deploy/aliyun
docker compose up -d --build
curl -fsS --retry 12 --retry-delay 2 --retry-connrefused http://127.0.0.1:8000/health
```

若备份、拉取、构建或健康检查任一步失败，停止继续操作，保留备份和错误输出。查看容器状态及应用日志：

```bash
cd /opt/shuran-app/deploy/aliyun
docker compose ps
docker compose logs --tail 120 app
```

健康检查应显示`version: 2.0.18`和`ui_version: 20261022conditions1`。这只证明服务响应，仍需用本人账号核对旧数据、启动条件和实际使用；APK下载仍是此前已发布的2.0.17，等待单独构建发布。
