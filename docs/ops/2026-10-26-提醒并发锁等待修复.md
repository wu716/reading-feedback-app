# 提醒并发锁等待修复（2.0.42）

## 生产证据与原因

2026-10-26 用户提供的诊断显示，容器内和宿主机访问 `/health`、`/ready` 均连接成功但收不到 HTTP 响应；PostgreSQL 正常运行，存在一个长期 `idle in transaction` 的持锁会话及等待该事务的会话。

Python 主线程栈停在 `get_reminder_settings → _setting_response → record_status → read_range → sources → settle_expired` 的同步 `SELECT ... FOR UPDATE`。提醒路由声明为 `async def`，却直接使用同步 SQLAlchemy Session；锁等待占住 Uvicorn 事件循环，健康接口和其他请求也无法响应，依赖清理无法及时推进。页面启动会并行请求提醒设置与待处理提醒，而普通读取也无条件获取用户行锁，放大了这一问题。

持锁会话的最后 SQL 与待处理提醒筛选反馈提交的代码相符，但现有日志没有 HTTP 请求与数据库 PID 的直接关联；该请求身份属于推断。主线程在提醒设置同步锁查询中阻塞、进而影响全站响应，有线程栈直接佐证。

## 实现

- 提醒、日程、旧版待办路由及调用日程完成逻辑的工作片入口改为同步路由，由 FastAPI 在线程池执行；内部同步调用同时调整。
- `settle_expired` 先检查是否确有到期计时片段，仅在需要结算时获取用户行锁，并在加锁后重新查询，避免并发请求重复结算。保留原有 flush 行为。
- 任务完成、执行计划保存、恢复及丢弃暂停状态明确获取写锁；执行计划首次创建时加锁并重新检查，保留原有写入串行保护。
- 提醒设置响应和待处理提醒状态计算完成后提交事务，使到期结算持久化并及时释放用户行锁。
- 不新增表或字段。截止时间、自动休息、历史记录与原客户端接口保持兼容。

## 验证与边界

使用项目 `.venv` 的 FastAPI 0.104.1、SQLAlchemy 2.0.35，测试客户端 httpx 0.27.2，85 项测试通过。覆盖提醒、日程、工作联动、反馈、项目执行、阶段日程。新增回归覆盖：提醒查询阻塞时异步健康探针仍响应；无到期片段时不获取用户行锁；提醒读取保存到期结算且重复读取不重复生成休息片段。
