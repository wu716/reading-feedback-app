# 书然：每次需求的最小回归执行

## 目的与边界

按需求实际影响选择测试，不每次运行全仓或制作全套独立 Demo。此流程只提供可复用的选择、检查和停止点；测试通过不能替代用户对重要视觉、交互或业务语义的验收。生产数据和部署仍按协作手册处理。

## 变更卡（修改前填写，控制在一屏）

| 项目 | 记录 |
|---|---|
| 原始需求与验收 | 引用用户原话，列可观察结果 |
| 允许改变 | 入口、字段、样式、接口中实际要变的部分 |
| 必须保留 | 用户已确认行为与当前业务依赖，注明来源 |
| 影响范围 | 本次文件、直接调用者、共享样式／数据消费者 |
| 基线与检查 | 修改前定向命令、已知失败；修改后同组命令和人工路径 |
| 停止与回退 | 何时停止合并；源码与数据分别如何恢复 |

先用 `git status --short` 和 `git diff --name-only` 核对工作区，再在命中的模块用 `rg` 查调用者；发现共享入口、模型、样式后才扩展搜索。脏工作区必须把本次文件显式交给测试选择器，不把其他人的未提交文件混进影响分析。

## 选择与运行

以下命令由 Codex 在项目中执行，用于建立和复核测试证据；用户无需在每次需求中手工运行。用户审核的是测试结果、风险和需要亲自体验的产品行为。PowerShell，项目根目录：

```powershell
Set-Location D:\projects\reading-feedback-app
.\.venv\Scripts\python.exe -m pip install -r requirements-test.txt
$env:SHURAN_NODE = 'D:\UserData\DevTools\Cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe'
$env:PLAYWRIGHT_PACKAGE = 'D:\UserData\DevTools\Cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules\playwright'
.\.venv\Scripts\python.exe scripts\regression_gate.py --paths app/routers/schedule.py static/js/daily-schedule.js
.\.venv\Scripts\python.exe scripts\regression_gate.py --paths app/routers/schedule.py static/js/daily-schedule.js --run
```

以上 Node 与 Playwright 路径是本机已有运行时；换电脑时设置为实际安装路径。选择器本身只用 Python 标准库。它按日程、长期目标账本和共享文件映射少量现有测试；应用文件未映射时退出码 2，需先查消费者并补选择规则。共享文件也先退出，确认影响后加 `--ack-shared`。不要将 `--ack-shared` 当作用户对中高风险产品变化的验收。

干净的独立检出可把 `--paths ...` 换成 `--base <修改前提交>`；在多人共用的脏工作区，优先 `--paths`。先在修改前运行一次选定测试并记录结果，再在修改后运行同组测试。脚本成功只打印简短结果；失败保留错误摘要并停止后续测试。对选择器没有覆盖到的直接消费者，另加对应测试命令，不能因为映射缺口宣称没有风险。

## 两个试点

- **既有行为基线**：`tests/test_workspace_schedule.py::WorkspaceScheduleTests::test_new_root_is_first_without_reordering_flow_or_children` 使用真实 FastAPI 路由、内存 SQLite 和合成账号，保护普通清单新任务在上、子任务仍归属原任务、主动重排后保存到数据库的流程顺序不变。`tests/test_schedule_hierarchy_ui.js` 保护浏览器中的普通清单与流程视图区分。
- **属性／变形测试**：`tests/test_ledger_properties.py` 对现有 `aggregate(days)` 生成最多 12 条消费与退款，检查金额守恒、分类净额之和、记录数；将记录分为两天并添加关联餐食，金额仍应不变。Hypothesis 每项固定 60 例、固定种子、不落盘案例库；仅测试纯函数，接口保存与账号隔离仍由原有 `test_long_term_details.py` 覆盖。

试点期间发现的**现存缺陷**：数据库中的 `flow_order=0` 在普通清单重排后仍正确，但日程接口序列化使用 `task.flow_order or task.sort_order`，会把 0 误当缺省值。已加严格 xfail 单独标记，未在测试基础设施任务中修改业务逻辑；修复时应让该用例转为正式通过。此已知失败不能用来豁免其他新失败。

## 什么时候扩大检查

| 修改位置 | 默认自动检查 | 追加人工验收 |
|---|---|---|
| 日程局部 | 日程 API、真实页面层级与入口 | 写任务、拆分、更多、流程、靠后任务返回位置 |
| 长期目标账本 | 明细接口、汇总属性与饮食图片入口 | 老记录、退款与关联餐食、不重复计钱、手机布局 |
| `static/index.html`、共享 CSS、模型、数据库入口 | 日程与长期目标代表性测试；选择器要求确认共享影响 | 实际改动的每个页面、半屏／手机与旧数据路径；必要时扩展测试 |

截图只在视觉变化区域保留前后对照；不自动批准新截图。变异测试不进入每次门禁。本次 Windows 环境不安装 `mutmut`：其当前版本需 `fork`，Windows 要在 WSL 运行；在内存副本中将净额计算的减退款改成加退款，属性测试检出该单点变异。一次检出不等于变异覆盖率。

## 完成条件

Codex 将定向测试与人工路径结果、已知失败、未验证项和最终 diff 一起报告，不把测试命令当作用户待办。发生新失败、范围外变化、数据兼容不明或中高风险尚未人工验收时停止合并或推送。通过后只提交本次文件；生产部署由用户执行，源码提交、GitHub 推送、部署和真实手机验收分别报告。
